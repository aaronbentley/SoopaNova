# SoopaNova

Next.js app that turns gaming screenshots into physical prints (posters, canvas, framed prints). A learning side project: deployed on Vercel at soopanova.app, but not actively marketed.

**Stack:** Next.js 16 App Router (Turbopack) · React 19 · TypeScript 5.9 · Tailwind v4 + shadcn/ui (`base-vega` style on Base UI, `@base-ui/react`) · Clerk v7 (auth) · Firebase (client Storage + callable Functions, Admin SDK Firestore) · Prodigi + Stripe (print fulfilment and checkout; being built on the `replatform-prodigi` branch) · Motion (`motion/react`, the homepage hero animation) · Vercel Analytics/Speed Insights · Yarn 4.

## Print flow

1. `/create` → `src/components/upload-file.tsx` (a thin component): signed-in user drops a JPG/PNG (`screenshot-dropzone.tsx`). `src/hooks/use-screenshot.ts` reads its dimensions straight away and rejects it (toast) if it's under the minimum, otherwise holds the file, preview url and dimensions. There's no separate preview step: `upload-file.tsx` then starts the pipeline and opens the print options sheet at once. `src/hooks/use-create-print.ts` runs steps 2–3 as one pipeline with a single `status` (`idle → uploading → moderating → ready`, or `flagged` / `error`). It supports cancel (a cancelled run's late results are ignored) and retry (an already-uploaded file isn't uploaded again).
2. Browser uploads to Firebase Storage as `{uuid}--{clerkUserId}--{filename}` (`react-firebase-hooks` `useUploadFile`).
3. Browser calls the `moderateImageUrl` callable (`functions/src/index.ts`, Cloud Vision SafeSearch). It downloads the upload and uses `sharp` (`functions/src/images.ts`) to make a 2048px JPEG copy that's sent inline to Vision (Vision rejects files over 20MB) and a 480px WebP thumbnail. It rejects `adult === 'VERY_LIKELY'` and writes the verdict to the file's custom metadata as `moderation: passed | rejected` (clients can't set it; see `storage.rules`). Approved uploads get their thumbnail at `thumbnails/{name}.webp`: outside the root, so clients can't reach it, and covered by the 3-day lifecycle (orders will copy it somewhere permanent). The retention policy blocks overwrites, so a retry keeps the existing thumbnail. The function runs with 1GiB memory and caps input at 100 million pixels.
4. The **print options sheet** (`src/components/print-options/`) is open throughout: the preview shows upload progress, "Checking your screenshot", a flagged notice (options locked) or an error with "Try again" (`preview-status.tsx`), and an ⓘ button opens the screenshot details (`screenshot-details.tsx`, reusing `image-metadata.tsx`). Checkout waits for `ready`. The sheet has: delivery country (UK, EU 27, US; detected from the browser language and remembered in localStorage by `src/lib/delivery-country.ts`), product type, size and Prodigi options (frame colour, canvas edges), a preview cropped from the centre like Prodigi's `fillPrintArea`, the price, "+ shipping from", and the personal-use confirmation. It's a react-hook-form form (`usePrintOptionsForm` in `src/hooks/use-print-options.ts`) validated by zod (`printOptionsSchema` in `src/lib/print-options-schema.ts`). Product, size and options depend on each other and on the country, so each change re-resolves the whole selection (`resolveSelection`) and every field always holds a valid value; "Continue to checkout" stays disabled until the personal-use confirmation is ticked, and zod checks it again on submit (and the server at checkout); sizes are graded by pixels per inch (`src/lib/print-quality.ts`: Great ≥150, Good ≥100, OK ≥75, below that not orderable). Product descriptions and tags are in `src/assets/data/products.ts` (shared with the homepage), swatches and default options in `print-options.ts`, countries in `countries.ts`. "Continue to checkout" (`use-checkout.ts`) sends the selection and the upload's Storage name to the `startCheckoutAction` Server Action (`src/actions/checkout.ts`), a thin wrapper around `startCheckout` in `src/lib/checkout.ts` that returns the Checkout url or a message for the customer (`CheckoutError`). That validates the request with `checkoutRequestSchema` (the same zod rules plus `fileName`: product type, size sold in the country's region, every option, the confirmation), checks the upload is the caller's own and `moderation: passed` (`src/lib/uploads.ts`), prices it server-side (`getPrice`), and runs the **margin guard**: a live Prodigi quote for the exact SKU, options and country (`getQuoteCosts` in `src/lib/prodigi-costs.ts`, shared with the catalogue script) must leave at least the product type's `minMargin`, or checkout is refused. It then adds a print session (`status: 'checkout'`, the product, options, price, charged shipping, Prodigi's costs, and the personal-use confirmation with `termsVersion` from `src/assets/data/legal.ts`) and creates a Stripe Checkout session (`src/lib/stripe.ts`): one line item with the thumbnail as its image, Standard/Express `shipping_options` at the live shipping cost rounded up (each with `metadata.prodigiShippingMethod`), the delivery country locked, phone collection, `metadata`/`client_reference_id` with the print session id, and a 1-hour expiry. Stripe returns to `/orders/?checkout=success` or `/create/?checkout=cancelled` (`checkout-toast.tsx`).
5. **Paid → order → Prodigi:** `src/app/api/webhooks/stripe/route.ts` verifies Stripe's signature (`STRIPE_WEBHOOK_SECRET`) and hands `checkout.session.completed` / `async_payment_succeeded` to `fulfilCheckout` in `src/lib/orders.ts` (`checkout.session.expired` marks the print session `expired`; `charge.refunded` goes to `recordRefund`, which finds the order through the payment intent's metadata and keeps the running total as `refund: { amount, full }`). It re-fetches the session (expanding the shipping rate for its `prodigiShippingMethod`), then in one transaction claims the print session (it must match the Stripe session and have no `orderId`) and creates the order in `customers/{userId}/orders` (`ordersCollection`) with `status: 'paid'`: the session's product and costs, what Stripe charged (`amounts`, `promotionCode`), the delivery `recipient` in Prodigi's format and the personal-use record. It copies the moderation thumbnail to `orders/{orderId}.webp` and submits the order to Prodigi (`createOrder`: `idempotencyKey`/`merchantReference` = order id, `fillPrintArea`, a 3-day signed url to the original upload, `recipientCost`, and a `callbackUrl` with `PRODIGI_CALLBACK_SECRET` when set), then saves Prodigi's order onto ours (`saveProdigiOrder`: `status: 'submitted'` and `prodigi` = stage, details, issues, shipments with tracking, `lastUpdated`, `outcome`). Prodigi's **order edit window** (2 hours, set in its dashboard under Settings → Preferences) pauses every order before production, so a new order's outcome is `OnHold`; `OnHold` and `AlreadyExists` replies carry only the order id, so `createOrder` fetches the order. Stripe retries anything but a 2xx, so every step resumes safely: a claimed session returns its existing order, and a repeat submission gets Prodigi's `AlreadyExists` (the same Prodigi order). Prodigi refusing an order (4xx) sets `status: 'failed'` with `error` and answers 200 (retrying won't help); other errors answer 500 so Stripe retries. Local dev and the preview share the Stripe sandbox, so both receive every event: checkout records its `origin` in the session and payment intent metadata, and `isOwnCheckout` makes the dev server (`NODE_ENV=development`) handle only checkouts started on localhost and deployments only the rest. The webhook route has no Clerk auth (it's in the ESLint rule's `public` list), and the endpoint needs the trailing slash (`/api/webhooks/stripe/`): Stripe doesn't follow redirects. Locally: run `yarn stripe:listen` alongside `yarn dev` (without it, local checkouts are paid but never become orders), and pay with card 4242 4242 4242 4242.
6. **Status updates:** Prodigi POSTs CloudEvents to `src/app/api/webhooks/prodigi/route.ts` (the `callbackUrl` with `?token=PRODIGI_CALLBACK_SECRET`, compared in constant time; also no Clerk auth). Callbacks aren't signed, so the body only names the order (`subject`): `syncProdigiOrder` fetches it with our API key and finds ours through its `metadata` (`userId`, `orderId`). `saveProdigiOrder` runs in a transaction and only replaces the snapshot when Prodigi's `lastUpdated` is newer, so callbacks and the submission can arrive in any order. Prodigi also calls back when the edit window ends and the order goes into production. Prodigi can't reach localhost: test by POSTing `{"subject":"ord_…"}` to the local route with the token, or on the preview.
7. `/orders` (`src/app/orders/page.tsx`, `src/components/order-list.tsx`) lists the user's 20 latest orders through the Admin SDK: thumbnail (`orders/{orderId}.webp` via a 1-hour signed url, `getSignedReadUrl`; the CSP allows `https://storage.googleapis.com`), product and options (`src/lib/print-labels.ts`, shared with checkout), date, total, a progress badge (`getOrderProgress` in `src/lib/order-status.ts`: Processing → Received → Printing → Shipped, or Cancelled / On hold), any refund, and tracking links. **Customer cancel:** for 90 minutes after ordering (`cancelWindowMinutes` and `getCancellableUntil` in `order-status.ts`, only while Prodigi hasn't started production (`stage: InProgress`, `details.inProduction: NotStarted`), well inside the 2-hour window; the sandbox has no edit window, so there it lasts until the sandbox moves the order on), `cancel-order-button.tsx` confirms and calls `cancelOrderAction` (`src/actions/orders.ts`) → `cancelCustomerOrder` in `orders.ts`: cancel at Prodigi first (the order must come back `Cancelled`), then a full Stripe refund (idempotency key `cancel-{orderId}`), recording `cancelledAt`, `cancelledBy` and `refund`. To cancel by hand (a takedown, or after 90 minutes): cancel in Prodigi's dashboard first, *then* refund in Stripe; the callback and `charge.refunded` update the order. CanvasPop-era orders only have an id and a date. After `?checkout=success`, `checkout-toast.tsx` refreshes the page a few times because the webhook usually lands a few seconds after the customer. The `onOrderCreated` Firestore trigger only logs the order's ids for now (its path is hardcoded to `customers`, so sandbox orders don't fire it).

## Commands

```sh
yarn dev          # https://localhost:3000 (self-signed HTTPS, needed for Clerk)
yarn build        # production build
yarn lint         # ESLint CLI (flat config: eslint.config.mjs)
yarn typecheck    # tsc --noEmit
yarn format       # prettier --write .
yarn catalogue    # regenerate src/assets/data/catalogue.ts from Prodigi (needs PRODIGI_* in .env.local)
yarn stripe:listen  # forward Stripe test webhooks to yarn dev (needs the Stripe CLI, logged in)

# Cloud Functions (separate npm package, NOT part of the Yarn project)
npm --prefix functions install
npm --prefix functions run build
npm --prefix functions run serve   # emulator; needs firebase-tools
```

Before calling a change done, run `yarn typecheck && yarn lint && yarn build`. There are no automated tests yet.

## Layout

- `src/app/`: routes. `api/` holds the route handlers: `firebase/token`, `webhooks/stripe` and `webhooks/prodigi`. Metadata routes: `opengraph-image.tsx` (the dark hero, via `ImageResponse`), `icon.tsx` (an SVG `Response`; `favicon.ico` is its fallback for older Safari, built from the same design), `apple-icon.tsx` (180px PNG), `sitemap.ts`, `robots.ts`. The generated images take the dark theme's colours as hex from `src/lib/brand-colors.ts` (Satori and favicon SVGs can't read `globals.css` or oklch), so update it when those tokens change.
- `src/proxy.ts`: Clerk `clerkMiddleware()` (Next 16's replacement for `middleware.ts`). It doesn't protect any routes (`createRouteMatcher` is deprecated); see the auth gotcha below. Its handler copies Vercel's `x-vercel-ip-country` header into a `visitorCountry` cookie (set when missing or changed; there's no header in local dev). `detectDeliveryCountry` in `src/lib/delivery-country.ts` picks the country for prices: the remembered choice, then that cookie (if we deliver there), then the browser language, then the UK. The Privacy page describes the cookie.
- `src/components/ui/`: **shadcn-generated** from the `base-vega` style (Base UI primitives; there's no Radix left). Update through the shadcn CLI (`npx shadcn@latest add <component>`, `--overwrite` to replace an existing file); don't hand-edit. These files use shadcn's own formatting and are in `.prettierignore`. Local edits to re-apply if a component is regenerated: `ui/sonner.tsx` imports `useTheme` from `@wrksz/themes/client` rather than `next-themes`, and don't keep the `next-themes` dependency the CLI adds. The CLI writes `import { cn } from "cn"` (shadcn's `cn` package) and adds that dependency; change it to `@/lib/utils` like the other ui files, and don't keep the `cn` package. The components need `@import 'shadcn/tailwind.css'` in `globals.css` (custom variants such as `data-open`, `data-checked`, `data-horizontal`). Base UI uses `render` instead of `asChild` (`<DropdownMenuTrigger render={<Button variant='ghost' />}>…</DropdownMenuTrigger>`; add `nativeButton={false}` when `render` isn't a button), menu items use `onClick` (not `onSelect`), a `DropdownMenuLabel` must sit inside a `DropdownMenuGroup`, checked state is `data-checked` (not `data-state=checked`), and `Select` needs `items` for `SelectValue` to show labels rather than values. Base UI radios and checkboxes render spans, not buttons, so a `<fieldset disabled>` doesn't disable them: pass `disabled` explicitly.
- `src/actions/`: Server Actions (`'use server'` files), one file per feature, e.g. `checkout.ts`, `orders.ts` (customer cancel). Each checks auth itself, validates its input with the zod schema from `src/lib/`, keeps the logic in `src/lib/`, and returns messages for the customer rather than throwing (Next hides thrown errors in production). Webhooks and anything an outside service calls stay route handlers.
- `src/content/`: long-form copy as MDX: the FAQ, Terms, Privacy, About, the screenshot guides (`screenshots/`) and Sustainability's "The honest bit". Write it as plain Markdown: the only non-Markdown is a `<Section>` line around each `##` heading and its paragraphs (it takes an `id` for anchors, e.g. the guides' platform tiles), a `<Callout title='…'>` around Markdown paragraphs for a note in an alert box, and imported data values such as `{sizeRange}`, so prices and sizes are never hardcoded. Numbered steps are `1. **Step title:**` with the details as a nested `-` list. Links: site paths (`/terms/`) use `next/link`, `social:twitter` / `social:instagram` / `social:threads` resolve to the `APP_SOCIAL_*` profiles, and other urls open in a new tab; a link title goes in quotes after the url. Escape a `[` that follows a backslash (`\\[`), as in Steam's paths. How it renders is set in `src/mdx-components.tsx` (required by `@next/mdx`; maps `h2`, `h3`, `p`, lists, emphasis and links to the inner-page components, and `Section` to a `PageSection` with the prose pages' tighter `md:py-10`; `Section`, `Callout` and the link component `TextLink` live one per file in `src/components/mdx/`, imported directly with no barrel file); `src/types/mdx.d.ts` references the `.mdx` module types. Each `page.tsx` stays the shell (metadata, `PageHeader` and platform tiles, the ESLint `public` entry, the Terms/Privacy "Last updated" date) and renders the content, passing per-page overrides as `components` (the guides use the default-padded `PageSection`). Pages built mostly from data and components (home, `/prints`, product pages, `/screenshots`, Sustainability's cards) stay TSX. Structured data stays in `src/assets/data/`, and UI microcopy stays in its components. Prettier formats `.mdx` (`_` emphasis, 4-space list indents).
- `src/components/`: app components. `src/components/account/`: the `/account` sections and the re-verification dialog. `src/hooks/`: client hooks (screenshot selection, print pipeline, post-sign-in navigation). `src/assets/data/`: static content (nav links, the homepage's steps in `steps.ts` and product photos in `product-images.ts`, product copy and the size range in `products.ts`, the product pages' longer copy, features and specs in `product-pages.ts` (`/prints/[product]/`, one static page per product type via `generateStaticParams` with `dynamicParams = false`), `/prints/sustainability/` (claims limited to what Prodigi states for our products, per the CMA Green Claims Code; it's a static folder next to the dynamic `[product]` segment), the `/prints/` comparison (its `compare` rows and `bestFor` lines are in `product-pages.ts` too; option counts come from the catalogue, which only keeps options that ship to all three markets), `size-range.ts` (kept out of `products.ts` so the header's client bundle doesn't pull in the catalogue), screenshot guide platforms in `platforms.ts` (`/screenshots/[platform]/`, one static page per platform like the product pages, loading `src/content/screenshots/{slug}.mdx`; its anchor tiles come from `sections`, whose ids must match the MDX `<Section id>`s), keywords, and the JSON-LD in `json-ld.ts`: the homepage's Organization, WebSite and Service with its catalogue, and each product page's WebPage, BreadcrumbList and Product (stable `#product` ids shared by both; specs and options as `additionalProperty`; a per-region AggregateOffer holding one Offer per size). It's built from the same data as the pages and rendered by `components/json-ld.tsx`; check changes at validator.schema.org). Product claims must match Prodigi's spec for the SKU (their product API and pages); prices and sizes on content pages come from `pricing.ts`, never hardcoded. The homepage's "from" prices are worked out per region at build time and `product-price.tsx` shows the visitor's after hydration (`useSyncExternalStore`, so the page stays static).
- **Pricing** (Prodigi): `src/assets/data/pricing.ts` is the hand-edited config: regions (GBP/EUR/USD, each quoted for one country), product types with their Prodigi SKU family, sizes and margins, rounding, shipping methods and overrides. `scripts/prodigi-catalogue.ts` (`yarn catalogue`) reads it and writes `src/assets/data/catalogue.ts` (generated; don't edit): per SKU, its options, `printArea` pixels and per-region costs including Prodigi's tax. `src/lib/pricing.ts` turns them into prices (`getPrice`, `getShippingPrice`, `getMargin`), shared by the UI and server routes. The script runs with Node's built-in TypeScript support, so it imports `pricing.ts` by relative path with a `.ts` extension (hence `allowImportingTsExtensions`) and only `import type`s from `@/`.
- `src/lib/prodigi.ts`: the Prodigi Print API client (`server-only`): `createQuote`, `createOrder`, `getOrder`, `cancelOrder`, `getProductDetails`, throwing `ProdigiError` on HTTP errors and retrying rate limits (429) briefly. API types are in `src/types/prodigi.ts` (the catalogue script shares them). Prodigi returns business outcomes (`Created`, `OnHold`, `AlreadyExists`, `ActionNotAvailable`…) with HTTP 200, so check `outcome`. Callbacks aren't signed: fetch the order rather than trusting the body. Code that Node runs directly (the script, and anything it imports) can't use TypeScript-only syntax such as constructor parameter properties.
- **Analytics:** Vercel Web Analytics custom events (the Pro plan keeps 2 properties per event, so properties are readable labels such as `print: 'Canvas, 24 × 16″'`). Names and `printProperties` are in `src/lib/analytics.ts` (with `trackEvent` for the browser); `trackServerEvent` in `analytics-server.ts` sends after the response via `after()`. Events, in funnel order: `Screenshot uploaded` (`use-create-print.ts`, once per file: `resolution`, `format`), `Print option chosen` (each user change in `use-print-options.ts`: `choice`, `product`), `Checkout started` (`startCheckoutAction`), `Checkout failed` (also there: `reason` from `CheckoutError`, e.g. `margin` for the margin guard, or `error`; and `print`) `Order placed` (`fulfilCheckout`, only for the attempt that creates the order) and `Order cancelled` (`cancelOrderAction`: `print`, `options`). Locally they're only logged (browser console / server terminal).
- `src/lib/firebase-admin.ts`: the only place the Admin SDK is initialised (`server-only`, modular `firebase-admin/app`, `/auth` and `/firestore` APIs). `src/firebase/config.ts` is the client SDK, and `src/firebase/sign-in.ts` signs it in to Firebase Auth.
- `functions/`: Firebase Cloud Functions (Node 24, firebase-functions v7, npm + `package-lock.json`). Deployed with the Firebase CLI, excluded from Vercel by `.vercelignore`, and excluded from the root tsconfig and ESLint.
- `storage.rules` / `firestore.rules`: Firebase security rules, deployed with the Firebase CLI. The Storage bucket has a 1-day retention policy and a lifecycle rule that deletes uploads and their moderation thumbnails after 3 days (not `orders/`): uploads are temporary and can't be deleted early.

## Conventions

- Customer-facing copy follows `docs/tone-of-voice.md` (sentence case, "Start creating" and "Browse prints" as the calls to action, calm errors, light pop-culture gaming flavour): playful headlines, plain and precise product facts, British English.

- Prettier config is in `.prettierrc.json`: 4 spaces, no semicolons, single quotes (JSX too), no trailing commas, `bracketSameLine`.
- Import alias `@/*` → `src/*`.
- Tailwind classes are usually passed to `cn()` as arrays: `cn(['flex', 'gap-2'], condition && ['...'])`.
- Short `/** ... */` block comments above logical steps. Match the surrounding density.
- Tailwind v4 is configured CSS-first in `src/assets/styles/globals.css` (oklch theme tokens, `tw-animate-css`). There is no `tailwind.config`.
- Use `react-firebase-hooks` for client-side Firebase interactions (deliberate choice; don't replace it with raw SDK calls).
- User input uses **react-hook-form + zod** with react-hook-form's `Controller` and shadcn's Field components (`Field data-invalid` / `FieldLabel` / `FieldError errors={[fieldState.error]}`, `aria-invalid` on the control); there's no shadcn `Form` wrapper. Keep the zod schema in `src/lib/` so the server route validates with the same rules. A label element can't name a radio group, so radio groups need `aria-labelledby` (see `FieldEyebrow` and `FieldRadioGroup` in `print-options/fields.tsx`), and pass `field.ref` to controls so react-hook-form can focus the first error.
- **Visual style** (from the Claude Design homepage handoff): near-black/white surfaces, hairline `border` lines between full-width sections, Geist for text and Geist Mono (`font-mono`) only for small labels, and the pink `primary` used sparingly as an accent. Use the theme tokens, not hex values. Shared pieces:
  - Utilities in `globals.css`: `wrapper` (1200px content width with 24px gutters; use it instead of `container`, which snaps to breakpoint widths), `eyebrow` (mono uppercase label), and `bg-grid` plus `mask-fade-top` / `mask-fade-bottom` (the faint grid backdrop).
  - Components: `Wordmark`, `Hero*` (grid, glow, pill, big heading; homepage and 404), `HeroStage` + `HeroStoryboard` (the homepage's full-width Motion SVG story under the actions: game screen → capture → upload → the screenshot springs up into a framed print; plays once in view, then a replay button; follows the theme; Lucide paths inline so strokes can draw on), `SectionHeader` (eyebrow, H2, sub), `PlatformTile` / `PlatformStrip` (hairline link tiles), `PageHeader` / `PageSection` / `Typography` (inner pages), and `ctaButtonVariants` in `cta-button.ts` (44px hero/CTA buttons). The shadcn `Button` is still used for smaller buttons.
  - The homepage upload button is `<UploadFile variant='button' />`. The create page uses the default dropzone variant.
  - Main nav: `src/assets/data/links.ts` (Create, Prints, Screenshots, About, FAQ). Links with `children` open a panel on desktop (`main-nav.tsx`, shadcn `navigation-menu` on Base UI, led by the `overview` link to the index page) and are indented in the mobile sheet. Trigger states use `navTriggerClassName`, because the ui component's `data-popup-open:`/`focus:` classes otherwise override the active pink.
- Theming uses `@wrksz/themes` (not `next-themes`). `ThemeProvider` from `@wrksz/themes/next` is used directly in the server `layout.tsx`, and `useTheme` comes from `@wrksz/themes/client`. It defaults to the system theme and stores the choice in localStorage under `theme`.
- Clerk v7: use `<Show when='signed-in' | 'signed-out'>` (`SignedIn`/`SignedOut` no longer exist). No Clerk UI components are rendered (see the custom auth UI gotcha).

## Environment

- Copy `.env.example` → `.env.local`. `NEXT_PUBLIC_*` values reach the browser. The rest are server-only.
- Firestore collection names come from `FIREBASE_FIRESTORE_COLLECTION` / `FIREBASE_FIRESTORE_SUB_COLLECTION`. The `onOrderCreated` trigger path in `functions/src/index.ts` is hardcoded and must match them in production. Local dev and Preview use `customers-sandbox`, so test checkouts and orders stay out of the real collection.
- Order thumbnails live at `orders/` in the uploads bucket and are kept: the lifecycle rule only matches the prefixes `0`–`9`, `a`–`f`, `-` (uploads start with a uuid) and `thumbnails/`. Anything stored under a new prefix is kept forever unless it's added to the rule.
- The Admin SDK key is `FIREBASE_SERVICE_ACCOUNT_PRIVATE_KEY` (escaped `\n` newlines are unescaped in code).

## Gotchas

- **Clerk is the source of truth for users; Firebase Auth mirrors it.** `POST /api/firebase/token` mints a Firebase custom token whose uid is the Clerk user id. `firebase-auth-sync.tsx` (in the root layout) signs Firebase in and out to match Clerk, and `useCreatePrint` calls `ensureFirebaseUser()` before uploading. `storage.rules` only let a user create and read their own `{uuid}--{uid}--{name}` files, and `moderateImageUrl` rejects unauthenticated callers and other users' files. Every Clerk user who uploads gets a Firebase Auth user with the same id. The client Auth instance is created with `initializeAuth` and **no** popup/redirect resolver. Don't switch it to `getAuth()`: that loads `apis.google.com/js/api.js` plus a hidden auth iframe, which the production CSP blocks.
- **Deploy order depends on the change.** Local dev talks to the production Firebase project too.
  - Auth changes (8.3): the app (Vercel) *before* the stricter `storage.rules` and functions, because an app that isn't signed in to Firebase can't upload under the new rules.
  - Moderation tagging (8.4): functions (and rules) *before* the app. Server routes refuse files without `moderation: passed`, and only `moderateImageUrl` writes it.
- **Every page, route handler and Server Function checks auth itself.** `proxy.ts` protects nothing. `@clerk/next/require-auth-protection` (in `eslint.config.mjs`) fails lint unless a resource under `src/app`, or any `'use server'` file, starts with `await auth.protect()` or an early return on `auth()`. The exceptions are the static pages in its `public` list, so add any new content page there. `/create`, `/orders` and `/account` call `auth.protect()`.
- **Keep pages static.** Every content page (home, about, faq, screenshots, prints and the product pages, legal, sign-in/up, 404) is prerendered; only `/create`, `/orders`, `/account` and the API routes are dynamic (they call `auth.protect()`). Anything in a server component that reads the request makes a page dynamic, and the header is on every page. That includes Clerk's `<Show>`, `auth()` and `currentUser()`: `<Show>` has a server version that calls `auth()`. So signed-in/out UI goes in client components (`header.tsx` is `'use client'`; `hero-upload-action.tsx` uses `useAuth`). `ClerkProvider` stays static as long as it isn't given `dynamic`. Check the `○`/`ƒ` markers in `yarn build` output after touching layout, header or auth UI.
- **CSP** lives in `next.config.ts` (production only). Add any new third-party origin there, or it will work in dev and break in production.
- **Node 25+:** `buffer-equal-constant-time` (via firebase-admin → jsonwebtoken) is patched in `.yarn/patches/` because `SlowBuffer` was removed. Keep the patch until upstream is fixed.
- **`jwks-rsa` is pinned to 3.2.2** (root `resolutions`). `firebase-admin/auth` requires `jwks-rsa`, and 4.x pulls in ESM-only `jose` 6, which Vercel's function loader can't `require()` even on Node 24. `firebase-admin.ts` imports `/auth`, so every route using the Admin SDK then fails to load. It works locally, so test with `node --no-experimental-require-module -e "require('firebase-admin/auth')"`. Remove the pin only once that loads without it.
- **Auth UI is custom (no Clerk UI components).** Sign-in/up is `auth-card.tsx`, using Clerk's `useSignIn`/`useSignUp` hooks: OAuth plus a 6-digit email code. An unknown email on sign-in becomes a sign-up, and a known email on sign-up becomes a sign-in. OAuth returns via `/sso-callback/` (`HandleSSOCallback`, imported from `@clerk/react` because `@clerk/nextjs` 7.9.9 doesn't export it; keep `@clerk/react` on the same version `@clerk/nextjs` uses). The header menu is `user-button.tsx`. `/account` handles email addresses, connected accounts, active devices and account deletion, and Clerk's re-verification for sensitive actions goes through `useReverified` and a custom email-code dialog (`account/reverification-provider.tsx`). So **sign-in settings in the Clerk dashboard aren't picked up automatically**: the instance is email code + Google/Discord/Microsoft, with passwords, MFA, passkeys and name fields off. Enabling one means code changes (`oauth-providers.ts` for providers; `auth-card.tsx` and `/account` for anything else). The prod instance has invisible bot protection, which mounts in `auth-card.tsx`'s `#clerk-captcha` and needs `challenges.cloudflare.com` in the CSP. Deleting a Clerk user doesn't delete their Firestore orders or print sessions.

- **`@clerk/eslint-plugin` is pinned to an exact version:** its rule is experimental and may break in minor releases before v1.
